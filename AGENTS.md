# Cruise development orchestration

These repository guidelines are subordinate to user, developer and system instructions.

- Inspect branch/status and the current runnable route before editing. Preserve unfinished work; use an isolated branch or reversible route. Never deploy without authorization.
- Prefer existing Three.js/R3F, audio hooks, vehicle assets and analytics contracts. Establish one coordinate system and shared interfaces before delegating.
- When delegation is authorized, assign bounded independent work with explicit file ownership. Keep integration with the lead. Record actual agent/model identifiers; never imply an unavailable model participated.
- Use specialist review for measured bottlenecks. Request an independent review of screenshots, gameplay and test artifacts rather than architecture alone. Do not duplicate broad audits.
- Radio visibility, usable touch controls and readable advertising are product requirements. Keep playback independent of driving/camera lifecycle.
- Measure continuous ad exposure with projected dimensions, view angle and occlusion. Distinguish geometric qualification from human readability. Do not count hidden signs or demo analytics as real sponsorship outcomes.
- Record browser/device, resolution, DPR, quality, sustained FPS and loading conditions. Emulation is not physical Android validation. JS heap is not GPU memory.
- Reuse licensed assets, maintain provenance, and request approval before spending or starting recurring services. Never infer target asset rights from a reverse-engineering tool license.
- Keep evidence and launch instructions under docs/cruise for each experiment. Clearly separate built, verified, failed, blockers and next action. Do not call unmet acceptance criteria complete.
